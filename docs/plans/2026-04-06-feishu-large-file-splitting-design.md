# Feishu Large File Splitting Design

## Goal

让飞书机器人在遇到超过飞书单文件上传上限的本地附件时，自动拆成多个分片文件连续发送，而不是报错或无响应。

## Problem

当前飞书附件发送链路会直接上传原文件。对于约 30MB 以上的文件，飞书接口会返回超限错误；在部分 SDK 场景下，这个错误还会表现成 JSON 解析异常，导致用户看到“没有回复”。

## Proposed Behavior

### 1. 保持小文件直发

当文件大小不超过飞书上限时，继续沿用现有 `send_file_path(...)` 逻辑，上传并发送单个文件，不改变当前体验。

### 2. 超大文件自动拆分

当文件大小超过飞书上限时：

- 不再直接拒绝。
- 按固定分片大小切成多个二进制分片。
- 每个分片命名为 `原文件名.part01`、`原文件名.part02` 这样的顺序格式。
- 顺序上传并发送每个分片。

分片文件使用临时目录承载，发送结束后自动清理，避免污染用户目录或长期占用空间。

### 3. 发送完成后补一条说明

当所有分片都发送成功后，机器人补发一条文本说明，内容包括：

- 原文件名
- 分片总数
- 在本机上的合并命令

默认使用 macOS/Linux 通用的 `cat part* > original` 方式说明，足够覆盖当前使用环境。

### 4. 分片失败时明确报错

如果任意一个分片上传或发送失败：

- 停止后续分片发送
- 返回明确错误，指出卡在第几片
- 不再出现“消息收到了但不回复”的情况

## Scope

本次只改飞书文件发送分支，不改：

- 图片发送逻辑
- 会话、模型、额度命令
- 最近附件判定与权限策略

## Testing

新增测试覆盖：

- 超大文件会自动拆分并发送多个分片
- 分片发送成功后会补发合并说明
- 任一分片失败时会返回明确错误
- 小文件仍保持原样单文件发送

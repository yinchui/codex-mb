# Feishu Compound Send Intent Design

## Goal

让飞书机器人正确处理“先做动作，再发给我”的复合请求，例如“把这个文件夹压缩成压缩包然后发给我”，避免现有附件快捷发送逻辑提前截走请求。

## Problem

当前普通文本处理会先尝试附件发送意图，再决定是否把文本交给 Codex。只要句子里包含 `发给我`、`把文件发来` 之类短语，就可能命中附件快捷发送分支。

这对纯发送句式是正确的，例如：

- `发给我`
- `report.pdf，把这个发给我`

但对复合动作句式会产生错误行为，例如：

- `把这个文件夹压缩成压缩包然后发给我`
- `生成一份总结再发给我`

这类句子真正想表达的是“先执行动作，再把结果作为附件发送”，而不是“立刻发送最近附件”。

## Proposed Behavior

### 1. 区分纯发送句式与复合动作句式

保留现有显式发送短语识别，但新增一个“复合动作发送意图”判断：

- 如果文本只有发送意图，没有明显动作词，继续走现有附件快捷发送逻辑。
- 如果文本同时包含发送意图和动作词，则不要拦截，直接交给 Codex 执行。

首批动作词保持小而明确，只覆盖这次真实需求附近的高频场景：

- `压缩`
- `打包`
- `归档`
- `生成`
- `导出`
- `截图`
- `保存`
- `整理`

### 2. 保持现有附件发送体验

以下行为不变：

- `发给我` 在存在最近附件时继续自动发送。
- `把 notes.txt 发给我` 继续优先匹配最近附件中的文件名提示。
- 多附件候选时继续要求用户回复编号。
- 没有最近附件时继续返回当前提示文案。

### 3. 让复合句真正落到执行链路

像“把这个文件夹压缩成压缩包然后发给我”这样的句子，应直接进入 `_run_prompt(...)`。这样 Codex 可以先执行压缩动作，并把结果保存到运行时附件目录，后续再由现有最近附件机制完成发送。

## Scope

本次只优化“是否拦截为附件快捷发送”的判定层，不改：

- Feishu 上传接口
- 最近附件状态结构
- 文件权限策略
- Codex 执行动作本身的提示词内容

## Risks

- 动作词列表过宽，可能让某些原本应直接发送的句子不再走快捷发送。
- 动作词列表过窄，仍可能漏掉类似“先处理再发”的句式。

为控制风险，本次先采用显式关键词表加测试覆盖，后续再根据真实对话补充。

## Testing

新增和更新测试覆盖以下场景：

- 纯发送句式仍走快捷发送。
- “压缩后发给我”这种复合句式不再走快捷发送，而是进入 Codex 执行。
- “没有最近附件”的纯发送句式仍返回帮助提示。
- 复合句式不会错误清空或触发附件编号选择状态。

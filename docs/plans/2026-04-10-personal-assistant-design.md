# 私人助手设计方案

日期：2026-04-10

## 背景

目标是把 Codex 改造成一个以飞书私聊为主入口的私人助手。它需要持续记住用户的长期信息与当前在做的事情，能够随着对话自动更新状态，并在“有必要的时候”主动通过飞书私聊提醒，而不是机械地定时播报。

当前已确认的基础条件：

- 主输入面是飞书私聊，而不是桌面线程
- 任务主数据源是用户与助手的对话
- 助手需要主动追问状态更新
- 主动提醒风格为平衡型
- 移动端触达方式是飞书私聊
- 现阶段私人助手工作区整体放在坚果云目录中，后续机器扩容后再考虑迁移本地
- 当前仓库已经具备飞书消息收发能力，可复用现有链路

## 目标

- 记住用户的长期稳定信息，例如偏好、工作方式、提醒风格
- 记住用户当前手头上的事情，并随着飞书对话自动更新
- 在必要时主动通过飞书私聊发出提醒或追问
- 尽量减少重复催促与无意义打扰
- 保持设计上可迁移，未来可把运行态迁回本地磁盘

## 非目标

- 现阶段不接入日历、邮箱、外部任务系统
- 现阶段不做独立常驻服务平台
- 现阶段不要求跨多设备并发修改状态
- 现阶段不在当前代码仓库中实现所有私人助手逻辑

## 总体方案

采用“飞书对话驱动 + 私人助手工作区 + Codex memory + 自动化巡检 + 飞书主动触达”的混合架构。

职责分层如下：

1. 飞书通道仓库
   - 继续负责收消息、发消息、owner 配对、会话桥接
   - 不承载用户的私人动态状态与私人 skill

2. 全局 AGENTS
   - 放长期通用行为规则，例如永远中文回复
   - 不存放私人任务状态

3. 私人助手工作区
   - 放私人助手专用 AGENTS、skills、状态文件、设计文档
   - 作为飞书私人助手会话的主要工作区

4. Codex memory
   - 只记录长期稳定的用户事实和偏好
   - 不记录高频变化的当前任务细节

5. 自动化
   - 定期巡检状态
   - 按条件决定是否需要主动提醒或追问

## 数据分层

### 1. 全局 AGENTS.md

位置：

`/Users/aa/.codex/AGENTS.md`

职责：

- 约束全局通用沟通规则
- 不承担私人助手的动态逻辑

适合放的内容：

- 永远用中文回复
- 总体沟通风格
- 高层提醒原则

### 2. 私人助手工作区 AGENTS.md

职责：

- 约束飞书私人助手会话的默认工作流
- 在对话开始前读取状态文件
- 限制追问数量与提醒方式
- 区分写入 memory 与写入动态状态的边界

适合放的内容：

- 每次收到飞书私聊消息时，优先检查是否涉及任务变化
- 只在必要时追问一个关键问题
- 动态任务写入 `state/work_state.json`
- 长期偏好写入 memory
- 主动提醒时遵守静默和冷却规则

### 3. Codex memory

职责：

- 存储长期稳定的个人信息

适合放的内容：

- 用户喜欢的提醒强度为平衡型
- 用户希望通过飞书私聊进行任务更新与主动追问
- 用户当前阶段把私人助手工作区放在坚果云目录中
- 用户对沟通风格和节奏的长期偏好

不适合放的内容：

- 今天在做什么

## 技能设计

### 1. `personal-assistant-chat`

用途：

- 处理飞书私聊中的用户消息

职责：

- 识别消息是否在表达任务状态变化
- 抽取新任务、进展、卡点、截止时间、偏好变化
- 在必要时追问一个关键问题
- 更新 `work_state.json`
- 仅把长期稳定事实写入 memory
- 给出简洁回复或建议

输入特点：

- 来源于飞书私聊
- 语句可能简短、口语化、上下文依赖强

### 2. `personal-assistant-watch`

用途：

- 供自动化定期巡检时使用

职责：

- 读取 `profile.yaml`、`work_state.json`、`reminder_log.jsonl`
- 判断当前是否存在值得打扰用户的事项
- 生成短飞书提醒或追问
- 记录提醒结果
- 若无需提醒则安静结束

## 自动化设计

### 1. `assistant-watch`

建议频率：

- 每小时巡检一次

核心逻辑：

- 固定频率巡检
- 非固定时机提醒

判断条件示例：

- 高优先级任务在阈值时间内没有更新
- 距离 deadline 足够近且最近没有推进
- `waiting` 状态超时
- 当前 `active` 任务数量过多
- 到达需要状态追问的窗口

无事发生时：

- 不发送消息
- 只保留必要日志

### 2. `assistant-weekly-review`

建议频率：

- 每周一次

职责：

- 提醒用户回顾本周重点
- 识别长期停滞项
- 清理疑似失效任务
- 询问是否需要调整当前主重点

## 飞书触达设计

飞书作为主输入面和主输出面，继续复用当前仓库已有能力。

需求：

- 飞书私聊接收用户消息
- 飞书私聊主动发追问与提醒
- 已完成 owner 配对后，默认只面向该用户触达

主动提醒消息建议结构：

```text
我想提醒你一件可能更值得现在处理的事：

事项：X
原因：距离时间点较近 / 已久未更新 / 当前焦点过散
建议下一步：Y

你可以直接回复：
1. 继续推进
2. 先暂停
3. 已完成
4. 稍后提醒我
```

## 提醒规则

### 应当提醒的情况

1. 截止风险
2. 高优任务久未更新
3. 等待项超时
4. 焦点过散
5. 到达周回顾窗口

### 只更新状态、不主动打扰的情况

- 用户刚在飞书里更新过
- 刚提醒过且仍在冷却期
- 事情不紧急且没有 deadline
- 用户明确要求暂不提醒
- 当前处于静默时段且无紧急风险

### 节流规则

- 同一事项 24 小时内不重复用同一理由提醒
- 非紧急情况下 4 小时内最多主动发一次飞书
- 用户若回复“稍后提醒”，则顺延下次提醒窗口
- 用户若回复“先别提醒”，则进入静默或暂停状态

## 错误处理与兜底

1. memory 写入失败
   - 不中断当前对话
   - 先记录到本地补写队列或备注

2. 状态文件异常
   - 自动保留备份
   - 回退到最近可用版本
   - 不因单次状态损坏连续骚扰用户

3. 飞书发送失败
   - 记录失败原因
   - 在合理间隔后重试一次
   - 避免无限重试

4. 任务理解不确定
   - 使用较低 confidence 标记
   - 优先在后续对话中追问一个关键问题确认

## 上线策略

建议分三阶段上线：

### 第一阶段：影子模式

- 记录状态
- 记录“本来会提醒什么”
- 暂不真的主动飞书提醒

目标：

- 校验任务理解是否准确
- 校验提醒判断是否过于敏感

### 第二阶段：半自动模式

- 开始发送低频追问
- 以保守提醒为主

目标：

- 校验手机端打扰感
- 校验用户回复是否容易被结构化

### 第三阶段：正式模式

- 开启完整的平衡型提醒策略
- 加入周回顾自动化

目标：

- 形成长期可用的私人助理闭环

## 实施顺序建议

1. 创建坚果云中的私人助手工作区
2. 创建工作区 `AGENTS.md`
3. 初始化 `state/profile.yaml`、`state/work_state.json`、`state/reminder_log.jsonl`
4. 编写 `personal-assistant-chat` skill
5. 编写 `personal-assistant-watch` skill
6. 让飞书私人会话优先绑定到该工作区
7. 创建 `assistant-watch` 自动化，先以影子模式运行
8. 观察几天结果后，开启低频主动追问
9. 稳定后再启用 `assistant-weekly-review`

## 决策摘要

- 采用混合架构，而不是纯 memory 或纯自动化方案
- 飞书私聊是主输入面，也是主提醒面
- 任务主数据源是用户与助手的飞书对话
- 长期信息进入 memory，动态任务进入状态文件
- 私人助手相关 skill 放在私人助手工作区，不放全局目录
- 现阶段工作区整体放在坚果云目录中
- 提醒机制采用“固定频率巡检，按需触发提醒”的策略
